# REQ-P4-04 — Reason Generation

## Traceability
- Source requirement: REQ-P4-04 (SPEC.md §2, Phase 4)
- Depends on: REQ-P4-01 (`action`, `decision_basis`), REQ-P4-02
  (`confidence`), REQ-P4-03 (`message_type`)
- Unblocks: none (last prompt of this phase); the P5 output-generation
  phase consumes this phase's assembled `DecisionRecord`

## Objective
Deliver the reason-string generator that turns `decision_basis` (already
named and non-generic per REQ-P4-01) into one short, human-readable
sentence naming the specific signal(s) that drove the decision — never a
templated restatement of the action (e.g. never "This message was muted.")
— and assemble the complete `DecisionRecord` (SPEC.md §1.5) by wiring
together every prior prompt in this phase into `run_decision_fusion`, the
batch entrypoint `code/main.py` calls.

## Context & assumptions
- Read `_PREAMBLE.md` first; inherit the Decision Record contract (§1.5)
  and the "no LLM in fusion" assumption (reason strings are template-
  assembled from named components, not generated by a model call).
- Assumes REQ-P4-01's `FusionResult`/`decision_basis`, REQ-P4-02's
  `compute_confidence`/`compute_signal_agreement`, and REQ-P4-03's
  `select_message_type` are all available exactly as those prompts define
  them.
- `dataset/sample_messages.csv`'s existing `reason` column (30 rows) is the
  style reference for tone and length (SPEC.md §6's open question on this is
  resolved here): one sentence, present tense, names a concrete cause
  ("A trusted group admin sent a time-sensitive update...", "The sender has
  a pattern of repeated forwards...", "Similar historical messages were
  ignored, dismissed, or muted by this user.") — never a bare restatement
  like "This message was muted because it is spam."
- The exact phrase-per-`decision_basis`-component templates below are a
  documented, style-grounded assumption; the calibration pass after this
  prompt (per `_PREAMBLE.md`'s ADR-004 note) may adjust wording but not the
  underlying rule that `reason` is assembled from named components, never
  free text.

```python
# code/router/decision/reason.py
from collections.abc import Mapping, Sequence

from router.safety.verdict import SafetyVerdict


def build_reason(
    action: str,
    message_type: str,
    verdict: SafetyVerdict,
    decision_basis: Sequence[str],
    signals: Mapping[str, object],
) -> str:
    """Return one short, human-readable sentence naming the specific
    signal(s) that drove this decision.

    Selects the single highest-priority named component present in
    decision_basis (priority order documented in Implementation details
    below) and renders it through that component's phrase template,
    substituting concrete detail from verdict/signals where the template
    calls for it (e.g. the actual risk_signals text for a safety-driven
    reason). Falls back to a content/action-derived generic sentence only
    when decision_basis is exactly ("no_signals",) — this is not a
    templated restatement of the action field, it still names what was and
    was not found (e.g. "no urgency, payment pressure, or safety risk").
    Never raises for well-formed input.
    """
```

```python
from pathlib import Path
from collections.abc import Mapping

from router.decision.trace import DecisionRecord
from router.dataset.loader import DatasetBundle
from router.ingestion.message import NormalizedMessage
from router.personalization.evidence import EvidenceBundle
from router.safety.verdict import SafetyVerdict


def run_decision_fusion(
    bundle: DatasetBundle,
    normalized: Mapping[str, NormalizedMessage],
    verdicts: Mapping[str, SafetyVerdict],
    evidence: Mapping[str, EvidenceBundle],
) -> dict[str, DecisionRecord]:
    """Produce one DecisionRecord per message_id in bundle.messages.

    Looks up each message's forwarded_count and business_accounts row from
    bundle (building the business index once per call via
    router.safety.gate.build_business_index, not per message), fuses the
    action, computes confidence, selects message_type, and builds reason,
    in that order, for every message. Raises DecisionFusionError if the
    four input mappings' key sets disagree with each other or with
    bundle.messages, or if the produced count does not match — the same
    defensive shape as run_safety_gate/run_personalization/
    run_media_ingestion.
    """
```

## Implementation details
1. `build_reason` priority order over `decision_basis` (first present
   component wins; `decision_basis` order from REQ-P4-01 already reflects
   this same priority, so this function walks a fixed priority list and
   returns on first membership, it does not scan `decision_basis` in its
   given order):
   a. `"safety_block:scam"` → `f"The message shows scam-risk signals ({verdict.risk_signals[0]}) and is muted regardless of sender history."`
      (uses the first named risk signal for a concrete, non-generic detail,
      satisfying REQ-P1-05's "name which signal fired" one level up).
   b. `"safety_block:spam"` when `message_type == "forward"` →
      `"The sender has a pattern of repeated forwards that this user usually ignores."`
   c. `"safety_block:spam"` otherwise →
      `f"The message shows spam signals ({verdict.risk_signals[0]}) and is muted regardless of sender history."`
   d. `"muted_group_mention_override"` →
      `"The group is muted, but you were directly mentioned, which raises this above the group's baseline."`
   e. `"borderline_safety_risk:scam"` or `"...spam"` present alongside a
      non-mute `action` → `f"The message has some risk signals ({verdict.risk_signals[0]}) that lower its priority, though not enough to mute it outright."`
   f. `"sender_dismissal_history"` →
      `"Similar historical messages were ignored, dismissed, or muted by this user."`
   g. `"group_muted_suppressed"` →
      `"This group is muted by the user, and there is no direct mention to override that."`
   h. `"quiet_hours_suppressed"` →
      `"This arrived during the user's quiet hours, so it is held back rather than delivered now."`
   i. `"sender_engagement_history"` when `action == "notify"` →
      `"The sender has a strong history of being opened and replied to by this user."`
   j. `"evidence_corroboration"` (no higher-priority component present) →
      `"This matches a pattern of similar past messages from this source."`
   k. Fallback (`decision_basis == ("no_signals",)`): branch on
      `message_type`/`action` for a still-concrete (not templated-generic)
      sentence, e.g. for `message_type == "unknown"`:
      `"The sender is unfamiliar, and the message shows no urgency, payment pressure, or safety risk."`;
      otherwise: `f"This {message_type} message shows no urgency, payment pressure, or safety risk for this user."`
2. `run_decision_fusion`:
   a. Validate `set(normalized) == set(verdicts) == set(evidence) ==
      set(bundle.messages["message_id"])`; raise `DecisionFusionError`
      naming any mismatched id(s).
   b. Build `business_index = router.safety.gate.build_business_index(bundle.business_accounts)`
      once.
   c. Build a `message_id -> forwarded_count` lookup from
      `bundle.messages.to_dict("records")` once (parse via the same
      blank-defaults-to-0 rule `router.safety.gate._parse_forwarded_count`
      uses — import and reuse it rather than reimplementing).
   d. For each `message_id`: `fusion = fuse_action(message_id, verdicts[id], evidence[id].personalization_signals)`;
      `confidence = compute_confidence(verdicts[id], evidence[id].personalization_signals)`;
      `message_type = select_message_type(verdicts[id], fusion.action, normalized[id], evidence[id].personalization_signals, business_index.get(normalized[id].business_id), forwarded_counts[id])`;
      `agreement = compute_signal_agreement(verdicts[id], evidence[id].personalization_signals)`;
      `reason = build_reason(fusion.action, message_type, verdicts[id], fusion.decision_basis, evidence[id].personalization_signals)`.
   e. Assemble `DecisionRecord(message_id=id, action=fusion.action,
      message_type=message_type, reason=reason, confidence=confidence,
      evidence_message_ids=evidence[id].evidence_ids,
      safety_confidence=fusion.safety_confidence,
      value_score=fusion.value_score, urgency_score=fusion.urgency_score,
      signal_agreement=agreement, decision_basis=fusion.decision_basis)`.
   f. Raise `DecisionFusionError` if the produced count does not match
      `len(bundle.messages)`.
3. `code/main.py`: after the existing `evidence = run_personalization(...)`
   call, add `decisions = run_decision_fusion(bundle, normalized, verdicts,
   evidence)`, and extend the printed summary with counts per `action`
   value (notify/digest/mute) — matching the existing style of the
   safety/personalization summary lines already printed.

  each asserting the returned string is non-empty, is a single sentence
  (no embedded newline), and is not a bare restatement of `action` (e.g.
  assert the string does not equal a templated
  `f"This message was {action}d."`-shape string); fallback branch for
  `decision_basis == ("no_signals",)` per `message_type`. Target:
  `tests/unit/test_reason_generation.py`.
- **Integration:** `run_decision_fusion` given mocked
  `normalized`/`verdicts`/`evidence` plus a small synthetic
  `DatasetBundle.messages` (covering a blocked-scam row, a muted-business
  row, and a clean-notify row), asserting one `DecisionRecord` per message
  with every field populated and `message_type`/`confidence` consistent
  with the fixtures; a mismatched-key-set case raises `DecisionFusionError`.
  Target: `tests/integration/test_decision_pipeline_integration.py`.
- **System:** extend `tests/system/test_p4_pipeline_system.py` (opened by
  REQ-P4-01) with an assembled-phase test: run P0 load → P2 ingestion
  (fake OCR/ASR clients, per the existing P2 test convention) → P1 safety
  gate → P3 personalization → P4 `run_decision_fusion` over a small
  synthetic batch (reusing `tests/fixtures/dataset_valid` or an equivalent
  fixture), asserting one `DecisionRecord` per input message and that the
  safety-override contract holds end to end (a synthetic blocked-scam
  message's `DecisionRecord.action == "mute"` regardless of injected
  favorable personalization fixtures).
- **Acceptance:** "reason MUST reference the specific signal(s) that drove
  the decision... not a templated restatement of the action" → the
  not-a-bare-restatement assertion in every `build_reason` unit test, plus
  an acceptance test asserting at least one concrete noun/detail from
  `verdict`/`signals` appears in the rendered string for each
  signal-driven branch (e.g. the actual risk_signal text for the scam
  branch).
- **Smoke:** `run_decision_fusion` runs on one synthetic message end to end
  without error.
- **Sanity:** a known-blocked fixture's `reason` still names the scam
  signal after unrelated changes elsewhere in this module.
- **Regression:** the P1-scope-disagreement fixture from REQ-P4-03 (high-
  forward spam-blocked message) is pinned to its `message_type="forward"`
  reason template, not the generic spam template, so a future edit to the
  priority order cannot silently swap them.
- **End-to-end:** a local dry run over a small slice (5-10 rows) of the
  real `dataset/messages.csv`, through the real P0-P4 pipeline with the
  real `build_ocr_client()`/`build_asr_client()` (which safely no-op into
  the REQ-P2-04 fallback path without an API key, per ADR-007) — asserting
  the run completes without error and produces one `DecisionRecord` per
  row with a non-empty `reason` and a `message_type` in
  `ALLOWED_MESSAGE_TYPES`. This is the local/mocked path, not a gated
  live-API e2e test — no live OCR/ASR/LLM behavior is required to pass.
- **API:** N/A — no external API interaction (this module never touches
  P2's OCR/ASR clients directly; it only appends to the pipeline once P2
  has already run).
- **UI:** the `reason` field is the one output column a human reads
  directly. Not a rendered-surface test, but a formatting check: each
  `build_reason` branch's output is asserted to be a single sentence
  (ends with `.`, no embedded newline, no leading/trailing whitespace) and
  under a reasonable length bound (e.g. 200 characters), matching
  `dataset/sample_messages.csv`'s observed style.

## Acceptance criteria (derived from SPEC.md, made executable)

  every `build_reason` unit test's not-a-bare-restatement assertion.

  message, with every field populated → proven by the integration and
  system tests.
- The full P0-P4 pipeline runs end to end over a real slice of
  `dataset/messages.csv` without a live API key → proven by the local
  dry-run end-to-end test.
- `code/main.py` calls `run_decision_fusion` and reports a summary →
  verified by inspection (no dedicated test framework exists for CLI stdout

  way).
